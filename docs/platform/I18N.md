# Web UI Internationalization (i18n)

The VAF Web UI is localized using **next-intl**. All user-visible text should go through translation keys so the interface can be shown in multiple languages.

## Scope

- **In scope:** All visible text in the Web UI (Next.js app under `web/`): layout, main page, settings, connections, modals, toasts, tooltips.
- **Out of scope:** Backend and CLI messages are not translated by this system. Short fixed phrases the backend emits itself (e.g. the thinking-run nudge) are localized separately by the [Vocabulary Book](VOCABULARY_BOOK.md).

## Architecture

- **Library:** [next-intl](https://next-intl.dev/) (Next.js App Router).
- **Locale source of truth:** `web/lib/languages.ts` - list of `{ code, name, englishName, flag }` (endonym plus English exonym). Used by the language picker and optionally by the generator script. Shipped locales: German (`de`), English (`en`), Turkish (`tr`), Simplified Chinese (`zh`), Japanese (`ja`), Korean (`ko`), Thai (`th`).
- **Messages:** One JSON file per locale under `web/messages/` (`de.json`, `en.json`, `tr.json`, `zh.json`, `ja.json`, `ko.json`, `th.json`). Master locale for authoring is German (`de.json`); the CI guard `tests/test_i18n_catalog_parity.py` compares every other locale's keys and ICU placeholders against `en.json`, so a key or a `{placeholder}` that exists in one file only fails the suite.
- **Persistence:** The selected UI language is stored in `localStorage` under the key `ui_locale`. No backend sync.

## File Layout

```
web/
├── lib/
│   ├── languages.ts      # Supported locales (code, name, englishName, flag)
│   └── localeStore.ts    # Zustand store: locale, init(), setLocale()
├── messages/
│   ├── de.json           # German (master)
│   ├── en.json           # English (parity reference)
│   ├── tr.json           # Turkish
│   ├── zh.json           # Simplified Chinese
│   ├── ja.json           # Japanese
│   ├── ko.json           # Korean
│   └── th.json           # Thai
├── components/
│   └── IntlProviderWrapper.tsx  # Wraps app with NextIntlClientProvider
└── scripts/
    ├── generate-locales.js      # Create new locale files from master
    └── locale-codes.json        # Optional list for script (e.g. ["en", "tr", "zh", "ja", "ko", "th"])
```

## Adding a New Language

1. **Add the locale to the source of truth**  
   Edit `web/lib/languages.ts`: add `{ code: "xx", name: "…", englishName: "…", flag: "…" }` to the `languages` array (`name` is the endonym, `englishName` the English exonym shown as the secondary label in the picker).

2. **Create the message file**  
   From the `web/` directory run:
   ```bash
   node scripts/generate-locales.js xx
   ```
   This copies `messages/de.json` to `messages/xx.json`. Translate the values in `messages/xx.json`.

3. **Wire the locale into the app**  
   In `web/components/IntlProviderWrapper.tsx`: add `import xxMessages from "@/messages/xx.json"` and add `xx: xxMessages` to the message map. No change is required in `web/lib/localeStore.ts`; it validates codes via `isSupportedLocale()` from `languages.ts`.

4. **Optional:** Add the code to `web/scripts/locale-codes.json` if you use the script without arguments.

## Adding or Changing Translation Keys

- **Define keys in the master:** Edit `web/messages/de.json`. Use a clear structure (e.g. `layout`, `common`, `status`, `nav`, `main`, `auth`, `settings`, `connections`, `notifications`).
- **Use in components:**  
  - `const t = useTranslations('namespace');` then `t('key')`.  
  - For interpolation: `t('key', { count: n })` and in JSON use `"key": "RAG: {count} Treffer"`.
- **Update all locales:** After changing `de.json`, update `en.json`, `tr.json`, `zh.json`, `ja.json`, `ko.json`, `th.json` (and any other locale) with the same keys so no key is missing. The parity guard fails the build otherwise.

## Language Switcher

The UI language can be changed under **Settings → Interface → Language**. The control is a searchable popup (`web/components/settings/LanguagePicker.tsx`): a trigger button showing the active locale opens a centered dialog (the shared `web/components/ui/PickerDialog.tsx`, also used by the timezone picker) with a search field and the list from `web/lib/languages.ts`; each row shows the flag, the endonym and the English exonym, and the active locale carries a check mark. The search folds case and diacritics ("turkce" finds "Türkçe") and also matches the locale code; arrow keys, Enter and Escape navigate, and a click on the backdrop closes the dialog. The choice is persisted in `localStorage` and applied immediately.

## Generator Script

- **With arguments:** `node scripts/generate-locales.js en fr` - creates or overwrites `messages/en.json` and `messages/fr.json` from `de.json`. Use `--force` to overwrite existing files.
- **Without arguments:** If `scripts/locale-codes.json` exists and contains an array of codes, the script creates missing locale files (skips existing ones unless `--force`).

## Best Practices

- Use namespaces in `useTranslations('namespace')` to match the structure in JSON (e.g. `settings`, `main`).
- For new UI strings, add the key to `de.json` (and other locales) and use `t('key')` in the component; do not add hardcoded user-facing text.
- Keep the master locale (`de.json`) complete; other files can fall back to missing keys at runtime if next-intl is configured with a fallback locale.

## Per-language conventions

A locale whose typography or terminology needs decisions of its own gets a companion
document, and the machine-checkable half of it becomes a guard in
`tests/test_i18n_locale_style.py` rather than prose:

- [I18N_ZH_GLOSSARY.md](I18N_ZH_GLOSSARY.md) - Simplified Chinese terminology, sourced
  per term from Microsoft, Alibaba, Red Hat and the Chinese-native AI products, plus the
  punctuation, spacing and register rules the guard enforces.
- [I18N_JA_GLOSSARY.md](I18N_JA_GLOSSARY.md) - Japanese terminology, the long-vowel policy,
  and the register split by UI element type. Read it before editing a Japanese string: on
  spacing at a Latin boundary the Japanese rule is the exact opposite of the Chinese one.
- [I18N_KO_GLOSSARY.md](I18N_KO_GLOSSARY.md) - Korean terminology, the register, and the
  particle rule. Korean disagrees with both CJK neighbours on spacing and punctuation, and a
  postposition after an ICU placeholder cannot be resolved at authoring time, so it has its
  own mechanical rule that the guard enforces.
- [I18N_TH_GLOSSARY.md](I18N_TH_GLOSSARY.md) - Thai terminology, the register, and the
  spacing rule. Thai is written without spaces between words, so a space is punctuation
  here and the boundary rule inverts the Japanese one. The document also states how thin
  the Thai evidence base is compared with the other locales, which is why several terms in
  it are named as coinages rather than presented as vendor practice.

Three guards in the same file hold for EVERY catalogue, including `de.json` and `en.json`,
because none of them is a style choice:

- **An apostrophe never quotes a placeholder.** ICU reads the ASCII apostrophe as an escape,
  so `'{name}'` turns the placeholder into literal text and the value never substitutes.
  Use typographic quotes. The parity check cannot see this, because the token is still there.
- **A literal brace or an unclosed tag never shares a message with a placeholder.** ICU reads
  an unescaped `{` as the start of an argument and `<name>` as a rich-text tag, so a string
  showing a JSON snippet or a naming pattern looks like broken syntax and the whole message
  fails to parse. Two strings in every catalogue are in that shape and render correctly only
  because next-intl parses a message solely when a values argument is passed, and neither is
  called with one. Escape the braces as `'{'` and `'}'`, or close the tag, before giving such
  a string a placeholder.
- **No invisible characters.** U+200B, U+200C, U+200D, U+2060, U+00AD and U+FEFF survive a
  copy, a review and a diff without being seen, and they change what a search matches. The
  temptation is specific to Thai, which has no space between words, but line breaking is the
  renderer's job there: UAX #14 resolves Thai by dictionary lookup and every engine the app
  runs in ships that dictionary.

Two further guards watch the components rather than the catalogues, because a string that
never reaches a catalogue cannot be compared against one:

- **No user-facing copy written straight into JSX.** A string typed into a component is the
  same defect in every locale at once: it stays in whatever language its author used, and no
  translation round can find it, because the parity guard only compares catalogues against
  each other and the text is in neither. The sign-in and first-run path
  (`web/app/login/page.tsx`, `web/components/SoulWizard.tsx`) is held at **zero**, since it
  renders before and just after the language step. The rest of the interface carries a
  measured debt of 563 strings across 43 files whose per-file counts may only go down.
- **No error message assembled as a literal in a handler.** This is the same defect one
  layer down: it never appears in JSX, so the scan above cannot see it, and it fires
  exactly when the reader is least able to guess what happened. The sign-in path is at
  zero here too; the rest carries 48 across 16 files, pinned the same way.

## The sign-in surface

`auth.*` owns everything the reader sees before they are signed in: the boot screen, the
unreachable-backend notice, the login form and the two-factor step. It exists separately
from `onboarding.*` because those screens render twice over, once during first-run setup
and then again on every later sign-in, long after onboarding is over. Two rules follow:

- **The boot screen has no chosen language yet.** `localeStore.init()` reads the stored
  locale, falls back to the browser's via `resolveBrowserLocale()`, and only then to
  `defaultLocale`. That is why those strings still belong in the catalogue: they follow the
  browser rather than being frozen into one language.
- **An error on this path must come from the catalogue.** The language step is the first
  thing the user does, so a failure message falling back to English one screen later is the
  most visible form the defect takes. The guard holds this surface at zero for that reason.
